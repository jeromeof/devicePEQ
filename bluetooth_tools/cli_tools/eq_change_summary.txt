EQ CHANGE CAPTURE ANALYSIS - KEY FINDINGS
================================================================================

PROBLEM: Excessive "keepalive-like packets"
CAPTURE: eq_change.txt (2586 lines, 156 packets)

================================================================================
ROOT CAUSE IDENTIFIED
================================================================================

Each Command 0x6 query triggers a 193-byte Command 0xBD response!

Flow:
  APP → Command 0x6 (query filter status, 10 bytes)
  DEVICE → Command 0xBD (full PEQ config, 193 bytes)

Current behavior:
  - App sends Command 0x6 in BURSTS of 8-20 packets
  - Each burst triggers 8-20 × 193-byte responses
  - Total redundant data: ~4,600 bytes per burst

================================================================================
PACKET FREQUENCY ANALYSIS
================================================================================

Most frequent commands:
  Command 0x6:  45 packets (24 TX + 21 RX) ← MAIN CULPRIT
  Command 0xBD: 17 packets (1 TX + 16 RX)  ← TRIGGERED BY 0x6
  Command 0x4:  28 packets (26 TX + 2 RX)  ← Part of polling loop
  Command 0x3:  25 packets (8 TX + 17 RX)  ← Connect status polling

Repeating patterns detected:
  [18x] 0x6 → 0x6 → 0x6 → 0x6 → ... (up to 8 in a row!)
  [5x]  0x3 → 0x2 → 0x4 → 0x4 → 0x4 → 0x4 (status polling loop)

================================================================================
COMMAND 0x6 ANALYSIS
================================================================================

Structure: 05 5A 06 00 00 0A [filter_id] [preset/value] E8 03

Filter IDs observed:
  00, 01, 02, 03     - Left channel filters 0-3?
  10, 11, 12, 13     - Right channel filters 0-3?

Value byte (position 7):
  0xE4 (228) - Sent for filters 01, 02 only
  0xEF (239) - Sent for all filters 00-03, 10-13

Hypothesis:
  - E4 = Query active preset 228 (or modified filters only?)
  - EF = Query all filters in preset 239?
  - These values might be preset identifiers, not gain values

================================================================================
SOLUTION: STOP COMMAND 0x6 POLLING!
================================================================================

The app is continuously polling with Command 0x6, and each query triggers
a 193-byte Command 0xBD response. This creates bandwidth explosion.

Recommended changes:
  1. Remove Command 0x6 burst queries (24 packets → 0 packets)
  2. Send Command 0xBD query once when opening EQ tab
  3. Listen for unsolicited 0xBD broadcasts from device
  4. Reduce status polling (0x3, 0x2, 0x4) from 4-5 loops to 1

Expected bandwidth reduction:
  Before: ~4,600 bytes of redundant PEQ data per polling cycle
  After:  ~193 bytes (single query on demand)
  Savings: ~96% reduction in PEQ-related traffic
